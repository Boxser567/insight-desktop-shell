# 客户端构建知识体系设计

## 背景

客户端构建是因赛AI Desktop 的核心交付能力。2026-08-27 的 Core Runtime 升级暴露出多个跨仓库、跨平台和安装后运行问题。部分问题直到 GitHub 安装包构建或人工启动阶段才被发现，造成重复发布 Runtime、重复打包 Shell 和较长等待时间。

现阶段的 Core、Shell、插件及平台依赖仍在快速演进。构建流程不以一次成功为目标，而应尽早发现错误、缩小每轮验证范围，并在进入高成本步骤前设置明确的停止条件和人工验收点。

## 决策

构建知识拆成长期 Runbook 与单次事故复盘两层，并由现有发布说明提供统一入口。

### 长期构建 Runbook

新增 `docs/client-build-runbook.md`，维护可重复执行的构建验证曲线。内容包括：

- Core 与 Shell 的职责边界和升级顺序；
- 从低成本到高成本的分阶段验证流程；
- 每个阶段的输入、命令、成功条件和停止条件；
- 必须等待人工验证的节点；
- 本地缓存、独立输出目录和原生 runner 的使用原则；
- Release 资产、Runtime 锁、安装包内容及用户数据的核对清单；
- 遇到失败时如何回到最近一个已证明成立的阶段。

该文档只记录仍然有效的规则。后续构建经验改变规则时，直接更新 Runbook，不追加按日期排列的过程日志。

### 构建事故复盘

新增 `docs/incidents/2026-08-27-core-runtime-sidebar-build.md`，记录本次 Core Runtime 与 Better Sidebar 构建问题的完整复盘。内容包括：

- 变更背景和影响范围；
- 可观察症状和关键错误；
- 根因与修复之间的对应关系；
- 无效或证据不足的验证方式；
- 最终采用的本地与 CI 验证证据；
- 可以复用于后续构建的经验；
- 仍需后续改进的构建基础设施。

复盘保留事件事实，不承担当前操作规范。规则变化时更新 Runbook；历史复盘除事实纠错外保持稳定。

### 发布入口

扩充 `docs/release-runbook.md`，链接长期 Runbook 和事故复盘，并把以下要求设为发布入口检查：

- 重大 Core、Shell、默认插件或 upstream 更新前先阅读长期 Runbook 和相关复盘；
- 本地低成本检查未通过时禁止启动 GitHub 安装包构建；
- 需要人工判断的功能必须收到明确验收结果后才能进入下一阶段；
- GitHub Actions 成功只证明对应 job 完成，不能替代安装后功能验收。

## 验证曲线

长期 Runbook 采用逐级放大的验证曲线：

1. 确认变更范围、工作树和版本身份；
2. 运行定向测试、类型检查和文档或配置门禁；
3. 构建并检查 Core Runtime 的目标平台制品；
4. 更新 Shell 锁并验证下载、SHA-256、Runtime 元数据和关键文件；
5. 运行 Shell 全量测试、类型检查和普通 build；
6. 在独立输出目录生成目标平台 DEV 应用并检查包内资源；
7. 启动本地应用，验证全新 Profile、升级 Profile、Sidebar 及 HTML/Markdown 打开行为；
8. 等待人工验收；
9. 仅在前述证据完成后触发 GitHub 安装包构建；
10. 下载最终安装包并完成覆盖安装与首次安装验收。

任一阶段失败即停止，不通过重复触发更高成本阶段来收集本可在本地获得的信息。

## 维护规则

- 每次出现新的构建故障，先判断它是否改变长期流程；改变则更新 Runbook，否则只补充对应复盘。
- 命令必须与 `package.json` 和 GitHub workflow 保持一致，不复制已经失效的临时命令。
- 文档记录可观察证据和明确结论，不把猜测写成固定规则。
- 临时构建目录、用户数据备份和未跟踪文件必须标明所有权，禁止为了清理构建环境误删用户内容。
- 构建耗时优化优先减少重复下载、重复全量构建和无效 CI，不降低校验强度。

## 成功标准

- 新成员只阅读长期 Runbook 即可判断下一步应运行什么、何时停止以及何时等待人工验收；
- 同类 Core Runtime 或默认插件升级不会在本地功能未验证前触发 GitHub 安装包；
- 本次遇到的主要症状、根因和修复证据可从事故复盘中检索；
- `docs/release-runbook.md` 成为发布流程的稳定入口；
- 文档不依赖本机绝对路径、临时端口或仅对本次会话有效的状态。
