## 当前正常 Candidate 投放不能通过的门禁

1. 旧 Core 的 `SESSION_FORMAT_VERSION=3`，新 Core 为 4。JSONL 持久化读取最高代会话，旧实现明确拒绝高于自己 writer 的版本。保留 v3 前驱仅提供迁移输入，不能作为旧程序回退到前驱继续写入的依据。
2. 新版整体数据声明应为 `writesDataSchema=2`、`readsDataSchema=1..2`；独立 Profile 和账号存储 Schema 仍为 1。此处整体 Schema 2 表示与旧客户端不可原地恢复的组合，并非直接照抄 Session 格式号 4。
3. 公网 v1.0.3 三个目标均只声明读取 Schema 1。发布器 `publishV2Candidate()` 与客户端 `UpdateManager.check()` 都调用 `assertCandidateRecoveryCompatible()`，因此正常内测链路必须拒绝本次 Schema 2 组合。

不得通过保持 `writesDataSchema=1`、修改旧的签名 Manifest 或删除校验来投放。操作者已选择先交付具有独立 App ID / userData 的内部安装包；正式 Candidate 投放前仍需完成读取桥接。单纯“接受风险”不能让已经安装的旧客户端读懂 v4，也不能改变它内置的拒绝逻辑。

使用已发布旧 arm64 Runtime 与当前新 Runtime 做了实际隔离复现：旧 Core 创建并读取 v3 成功，新 Core 读取后写入 v4 成功，原 v3 文件仍保留；再次由旧 Core 读取同一个会话，明确拒绝 `uses log format v4, but this harness reads only v3`。证据为 `/private/tmp/insight-release-1.0.4-session-data-*.json`，仅涉及生成的测试会话。

公网证据：`/private/tmp/insight-release-1.0.4-public-baseline.json`，记录时间和全部签名校验结果；读取过程中没有修改 OSS/CDN。

## Windows 归档路径修复与全平台重试

[构建 37757880297](https://github.com/Boxser567/insight-desktop-shell/actions/runs/37757880297) 的三个目标均通过 `npm ci`，Windows 随后在 Runtime 解压失败：Git Bash 的 GNU tar 将归档参数中的 `D:` 盘符解释为远程主机，报 `Cannot connect to D: resolve failed`。按用户指示停止全平台：运行最终为 cancelled，两个 macOS 作业 cancelled，Windows 已失败，没有发布安装包或更新指针。

修复仅调整内部装配入口及相应测试：归档文件名传给 tar，归档目录作为进程 cwd，避免 GNU tar 对盘符的远程解析；测试的归档创建也采用相同的本地路径约束。增加含空格目录的实际创建、解压与来源校验回归。CI 在读取真实 Core 制品前先执行原生归档测试，再运行原有完整测试与打包校验。

本地 128 个文件、922 项测试及类型检查通过。Windows 与 Intel 的实际原生结果必须由新的 CI 验证，不能将 macOS 本地通过扩大为全平台结果。本轮仍未下载 Core 制品到本地。
